# 졸음운전 감지 기술서

팀 금쪽같은 우리 사이 (장범수 팀장, 김민영, 육주영) | 버전 2026-11-05 | 저장소 github.com/Jbs1214/geumjjogi-drowsy

이 문서는 기획서의 세부 내용을 옮겨 정리한 것입니다. 수치는 설정 파일(`config.py`, `rule_based/config.py`, `best_params.json`)이, DMD 라벨 변환 규칙은 라벨 JSON의 `rules`에 적힌 내용이 기준입니다. 값이 어긋나면 코드와 라벨을 기준으로 이 문서를 고칩니다.

## 0. 확정값 한눈에

| 항목 | 값 |
|---|---|
| 학습 창 | 3초, 15 FPS, 입력 모양 (45 × 11) |
| 이동 간격 | 학습 0.5초, 실시간 0.2초 |
| 모델 출력 | 비교용 4클래스 softmax (정상, 눈 감김, 하품, 고개 숙임), 최종 구성용 하품 전용 이진 모델 |

| 겹칠 때 우선순위 | 불확실 > 눈 감김 > 고개 숙임 > 하품 > 정상 |
| 졸음 단계 | 연속 눈 감김 1.5초 주의, 3초 졸음 |
| 켜짐·꺼짐 기준 | 0.6 켜짐, 0.4 꺼짐 (흔들림 방지) |

| 깜빡임 | 기본 기준은 눈 감김(짧은 감김도 `eye_closed`에 둠). NITYMED 기존 라벨은 아직 정상으로 되어 있음(5.5) |
| DMD 눈 감김 라벨 | close·closing 구간을 감음으로, opening은 뜸으로 봄(A 기준) |
| 하품 알림 | 5분 3회, 이후 2분 쿨다운, 끊김 1.0초 이하 병합, 하품 길이 상한 7초 |

| 제외 마스크 | 얼굴 미검출이거나 창 안 불확실 30% 이상 |

## 1. 입력과 특징

### 1.1 랜드마크 17개

MediaPipe Face Landmarker가 프레임마다 얼굴 좌표 478개를 내고(사전학습 모델, 직접 학습 없음), 이 중 눈 12개, 입 4개, 코끝 1개만 씁니다. 이보다 줄이면 EAR와 MAR를 정의할 수 없고, 번호만 고르는 것이라 추론 시간은 그대로입니다.

### 1.2 특징 11개

프레임당 11개이고, 모델 입력도 같은 11개입니다.

`face, ear_l, ear_r, ear, mar, pitch, yaw, roll, blink_l, blink_r, jaw_open`

| 지표 | 의미 | 사용처 |
|---|---|---|
| EAR | 눈 뜬 정도 | 눈 감김 판정, 모델 입력 |
| 연속 눈 감김 시간 | 처음 감은 시각부터 지금까지(초) | 주의·졸음 단계 판정과 경고 |
| MAR | 입 벌어진 정도 | 하품 감지, 하품 알림 |
| Head Pose | 고개 각도 | 모델 입력, 고개 숙임 처리(졸음 단계 기준은 아님) |

- 고개 각도(pitch, yaw, roll)는 점이 아니라 MediaPipe의 얼굴 변환 행렬에서 계산하므로 턱 끝 좌표는 넣지 않습니다.
- EAR는 Soukupová & Čech (2016)를 따릅니다.
- 클립별 얼굴 검출률을 확인해 80% 미만 클립은 따로 봅니다(야간 저조도, 안경 대비).
- 파일과 실시간 모두 `VIDEO` 모드로 프레임 시각을 넘겨 처리합니다(`landmarks/extract.py`).

## 2. 시간 처리와 학습 창

### 2.1 규칙과 모델의 차이

| 방식 | 시간을 다루는 법 |
|---|---|
| 규칙 기반 | 프레임마다 특징을 영상 시각과 함께 기록하고, "눈 감김이 연속 3초 이상" 같은 조건문으로 판단합니다. |
| 학습 모델 | 입력 길이가 고정이어야 하므로 시계열을 3초 창으로 잘라 창마다 정답을 붙여 학습합니다. 모델은 지금 상태까지만 답하고, 감은 시간은 규칙과 같은 타이머로 잽니다. |

### 2.2 창 만들기

1. 영상을 초 단위로 자른 뒤 15 FPS로 리샘플합니다. 데이터 FPS가 25(NITYMED)와 29.76(DMD)로 달라서입니다.
2. 3초 창은 45프레임이고, 입력 모양은 (45 × 11)입니다.
3. 창을 0.5초씩 밀며 잘라, 8초 영상이면 창 11개가 나옵니다.
4. 창마다 정답 하나(정상, 눈 감김, 하품, 고개 숙임)와 제외 마스크를 붙입니다.

### 2.3 이동 간격을 0.5초로 정한 이유

- 간격을 줄이면 창은 늘지만, 3초 창은 이미 인접 창끼리 5/6가 겹쳐 거의 같은 데이터입니다. 학습 시간만 늘고 얻는 정보는 적습니다.
- 0.5초는 하품 라벨 단위(0.5초)와 맞고, 1.5초 이상 지속되는 눈 감김과 하품도 놓치지 않습니다.
- 실시간 판정 간격 0.2초는 반응 속도를 위한 별개 설정이라 재학습 없이 바꿀 수 있습니다. 켜는 기준 0.6, 끄는 기준 0.4로 흔들림을 막습니다.

### 2.4 정답 규칙

| 클래스 | 정답 조건 | 이유 |
|---|---|---|
| 눈 감김 | 창의 끝 프레임이 눈 감김 구간 안 | 모델은 "지금" 눈을 감았는가만 답하고, 시간은 타이머가 잽니다. 창의 50% 기준이면 눈을 뜬 뒤에도 창에 감은 프레임이 남아 판정이 늦게 풀립니다(데모에서 평균 0.5초 지연). |
| 고개 숙임 | 끝 프레임이 고개 숙임 구간 안 | 현재 상태를 맞히는 클래스라 같은 이유입니다. |
| 하품 | 창의 50% 이상이 하품 구간 | 하품은 몇 초 이어지는 사건이라 한 순간으로 정할 수 없습니다. |
| 정상 | 위 어디에도 해당하지 않음 | |

여러 조건이 겹치면 불확실 > 눈 감김 > 고개 숙임 > 하품 > 정상 순으로 정합니다.
### 2.5 제외 마스크

불확실은 클래스가 아닙니다. 얼굴 미검출이거나 창 안 불확실 비율이 30% 이상인 창은 학습과 평가에서 뺍니다. softmax는 "모른다"고 답할 수 없어서 "판정 불가"는 규칙으로 만듭니다(3.3).

### 2.6 분할과 정규화

- 운전자 단위 분할 파일(`data/split.csv`)을 한 번만 만들어 모든 실험이 공유합니다. 같은 사람이 학습과 평가에 섞이지 않습니다.
- 분할 파일은 데이터와 함께 비공개 Drive로 공유합니다. 새로 만들 때는 `dataset.import_mini`로 만든 뒤 `dataset.dmd_convert --split train`으로 DMD 신규 운전자를 더합니다. NITYMED 분할은 `split_nitymed.csv`와 같습니다.

| 분할 | NITYMED | DMD |
|---|---|---|
| train | 22클립, 10명 | 13클립, 11명(1, 5, 6, 7, 9, 10, 13, 14, 23, 36, 37) |
| val | 6클립, 3명 | 3클립, 2명(29, 33) |
| test | 13클립, 8명 | 없음 |

DMD를 학습에 쓰는 이유는 야간뿐인 NITYMED에 주간 조건을 더하고, 손 가린 하품 정답이 DMD에만 있기 때문입니다. 따라서 DMD 평가는 학습에 쓰지 않은 val 운전자로만 내고, 16클립 전체를 평가 세트로 쓰지 않습니다. 최종 판정은 Test2입니다.

- 평균·표준편차 `norm.npz`는 학습 데이터로만 계산합니다.
- 운전자 단위 교차검증 결과도 함께 보고합니다.

## 3. 규칙 기반 판정

### 3.1 연속 눈 감김 타이머

- 눈 감김 상태는 규칙이면 EAR 임계값으로, 모델이면 눈 감김 확률(켜는 기준 0.6, 끄는 기준 0.4)로 정합니다. 임계값은 `calibrate`가 찾아 `auto_label/best_params.json` 하나로 공유합니다. 눈 감음 임계값은 `ear_ratio`(0.6) × 평소 EAR이고, 평소 EAR은 지금까지 들어온 검출 프레임의 EAR 75% 분위입니다. 이 파일에서 규칙이 쓰는 값은 `ear_ratio`뿐이고, 하품과 고개 숙임 기준은 3.2·3.3과 `rule_based/config.py`를 따릅니다.
- 눈을 감은 첫 시각부터 지금까지를 연속 눈 감김 시간으로 쓰고, 눈을 뜨면 처음부터 다시 잽니다.
- 0.1초(`min_close`)보다 짧은 감김은 노이즈로 봅니다. 15 FPS에서 약 1.5프레임입니다.
- 시간은 영상 시각 기준이고, 로그에는 실제 시각(`wall_time`)을 따로 남깁니다.
- 단계는 1.5초 미만 정상, 1.5초 이상 3초 미만 주의, 3초 이상 졸음입니다. Euro NCAP SD-202는 마이크로슬립을 1~2초, 수면을 3초로 정의하고, 1.5초는 그 범위에서 팀이 정했습니다. 연기 지침은 마이크로슬립 최대 4초, 수면 최대 7초입니다.
- 규칙과 모델이 같은 타이머를 쓰므로 비교가 공정합니다.

### 3.2 하품 알림 (졸음 단계와 별도)

| 항목 | 내용 |
|---|---|
| 하품 1회 | "하품 감지"를 몇 초 표시하고 단계는 바꾸지 않습니다. 하품은 졸리지 않아도 하기 때문입니다. |
| 알림 | 5분 안에 3회 이상이면 주의 표시, 이후 2분 쿨다운 |
| 병합 | 눈 감김이 우선이라 하품이 조각나므로(DMD 하품 30회가 128조각) 끊김 1.0초 이하는 한 번으로 셈 |
| 길이 상한 | 7초. 시작부터 7초가 지난 하품에는 끊긴 뒤의 판정을 잇지 않고 새 하품으로 셉니다. 끊기지 않고 이어진 긴 하품은 한 번입니다. 실시간 하품 알림 계산에만 적용하고, 라벨의 하품 구간은 상한 없이 그대로 씁니다(DMD 라벨에 7초를 넘는 하품이 있음). |
| 하품 중 눈 감김 | 눈 감김이 우선순위가 높아서(2.4) 하품 중에도 눈을 감으면 눈 감김으로 판정하고, 연속 눈 감김 타이머는 그대로 계속 셉니다. 타이머에서 제외하지 않습니다. |
| 최종 단계 | 눈 감김 단계와 하품 알림 중 높은 쪽 |
| 한계 | 손으로 가린 하품은 MAR로 못 잡아 하품 전용 모델로 보완합니다. 마스크를 쓰면 화면 스위치(`--mask`, Streamlit 사이드바)로 하품 감지를 끕니다. 마스크 영상이 없어 자동 감지는 넣지 않았습니다. |

### 3.3 고개 숙임, 판정 불가, 확인 필요 (졸음 단계와 별도)

고개 숙임은 절차서에 기준이 없어 졸음 단계의 기준으로 쓰지 않습니다.

고개 숙임은 정면 pitch보다 17.5도 이상 숙인 상태입니다. 정면 pitch는 세션 시작 60초 안에서 두 눈을 뜬 프레임(좌우 EAR 모두 0.2 이상)의 pitch 중앙값이고, 아직 없으면 절대 25도를 씁니다. 정면을 볼 때의 pitch가 카메라 위치에 따라 +1~+9도로 달라, 절대 기준만 쓰면 숙임을 늦게 잡고 눈을 감은 채 고개를 숙인 구간에서 타이머가 끊기기 때문입니다.

| 상황 | 동작 | 이유 |
|---|---|---|
| 눈 뜨고 고개 숙임 | "고개 숙임"만 표시, 경고 없음 | 휴대폰·계기판 보기는 졸음이 아닙니다. |
| 눈 감김 진행 중에 고개 숙임·눈 안 보임 | 이어받기: 눈 감김으로 계속 세어 합쳐 3초면 졸음. 눈이 보이고 뜬 것이 확인될 때까지 유지(상한 없음) | 가장 위험한 장면에서 경고가 끊기지 않게 합니다. 조건: 직전 눈 감김 0.5초 이상 |
| 눈이 안 보임(얼굴 미검출, pitch 초과, 선글라스) | "판정 불가" 표시(정상 아님) | 규칙으로 판단합니다. |
| 고개 숙임·판정 불가 3초 이상, 직전 눈 감김 아님 | "확인 필요" 경고 | 졸음 경고가 아니며 평가 지표에 넣지 않습니다. |

### 3.4 속도 신호

DDAW는 약 70km/h 이상에서 동작하도록 요구됩니다(2차 자료 기준, EU 규정 원문은 미확인). 데모는 속도 신호가 없어 항상 동작하며, 70km/h에서 3초는 약 58m입니다. Euro NCAP은 자발적 평가이고 법이 아닙니다.

## 4. 학습 모델

### 4.1 입출력

입력 (배치, 45, 11), 출력 4개 점수(정상, 눈 감김, 하품, 고개 숙임)에 softmax를 씁니다. 불확실은 출력이 아닙니다. 규칙과의 전체 비교에 씁니다.

하품 전용 모델은 입력이 같고 출력이 하품 점수 하나입니다. 정답은 창의 50% 이상이 하품 구간인지이고, 눈 감김과 겹쳐도 하품입니다. 최종 구성의 하품 판단에 씁니다. 확률 0.6 이상이 0.4초 이상 이어지면 하품으로 봅니다.

### 4.2 모델과 기준선

| 모델 | 비고 |
|---|---|
| 1D-CNN | PyTorch. 작은 모델로 충분하다고 봅니다. |
| LSTM | PyTorch. 작은 모델로 충분하다고 봅니다. |
| 기준선 | 창 요약 특징(특징별 평균·표준편차·최솟값·최댓값) + scikit-learn 로지스틱 회귀·랜덤 포레스트 |

두 모델은 같은 창 파일(`windows.npz`), 같은 분할 파일(`data/split.csv`), 같은 `norm.npz`, 같은 평가 기준을 써서 비교가 공정하게 합니다.

### 4.3 실시간 추론

최근 3초 창을 0.2초마다 판정합니다. 최종 구성에서 화면 단계와 경고음은 규칙의 눈 감김 단계와 하품 알림 중 높은 쪽을 따르고, 4클래스 모델은 비교 표시에만 씁니다. 하품 전용 가중치가 없으면 4클래스 판정으로 동작합니다. 추론 시간과 처리 속도는 규칙과 모델을 따로 잽니다. ONNX 변환은 우선순위 3번입니다.

## 5. 데이터와 라벨링

### 5.1 데이터셋

AI Hub는 지금 쓰지 않습니다(11.02 제외). 연출이 반복적이고 눈 감김이 0.5~1.5초뿐(3초 이상 0개)이라 졸음 기준을 평가할 수 없었고, 시간 정보와 정상 클립이 없었습니다.

| 항목 | NITYMED | DMD (졸음 부분) |
|---|---|---|
| 촬영 | 달리는 차, 야간(그리스, 대시보드 카메라) | 정차한 차, 주간(스페인, 얼굴 카메라 사용) |
| 운전자 | 21명 | 13명분(녹화당 약 3분: 정상, 졸림, 하품, 마이크로슬립) |
| 구성 | 하품 107편(15~25초), 마이크로슬립 21편(약 2분) | 사람당 영상 1개 |
| 형식 | mp4, 25 FPS | mp4, 29.76 FPS, 1280×720 |
| 라벨 | 없음 → 자동 라벨 후 사람 검수 | 프레임 단위 눈 상태·하품(고개 숙임 라벨 없음) |
| 조건 | CC BY 4.0, 논문 인용, 공개 가능 | CC BY-NC-ND 4.0, 학술용, 가공 자료 배포 금지 |

DMD를 고른 이유: 후보 4개(DMD, UTA-RLDD, YawDD, NTHU-DDD) 중 주간 실차, 정상 구간, 프레임 단위 눈 상태 라벨을 함께 주는 것은 DMD뿐입니다.

### 5.2 데이터 한계와 대응

| 사실 | 대응 |
|---|---|
| NITYMED는 야간만, DMD는 주간·정차만 있음 | 조명별 결과를 따로 내고, 실내 웹캠 조건은 자체 촬영으로 확인 |
| 3초 이상 눈 감김이 적음(DMD는 파일당 많아야 1~2회: gC_14 2회, gE_29 1회, NITYMED 마이크로슬립 클립 1편은 최장 1.64초. 전체 집계는 변환 후 기록) | 마이크로슬립 21편 우선 라벨링, 부족하면 졸음 평가는 자체 연기 영상(3~7초) |
| DMD에 고개 숙임 라벨이 없음 | 고개 숙임은 NITYMED 라벨로만 학습, 조명별 혼동행렬로 확인 |
| 깜빡임 기준이 출처마다 다름(DMD는 감김, NITYMED 기존 라벨은 정상) | 깜빡임(0.1~0.5초)은 단계 기준 1.5초보다 짧아 경고로 이어지지 않음. 다만 깜빡임 근처에서 확률이 0.4~0.6에 머물거나 연속 깜빡임(간격 0.3초 미만)이 이어 붙으면 감김이 길어 보일 수 있어, 데모 로그로 확인하고 필요하면 타이머의 최소 눈 감김 기준(현재 0.1초)을 조정. 결과표를 출처별로 나눠 기준을 적음. NITYMED 재라벨은 발표 이후 |
| NITYMED 파일명에 운전자 번호가 없음 | 영상을 보고 `driver_id`를 붙임 |

### 5.3 라벨 형식 (클립당 JSON 1개, 시간은 초 단위)

| 키 | 내용 |
|---|---|
| `clip`, `source` | 영상 이름 / 출처(`nitymed`, `dmd`, `self`) |
| `label_status` | `auto`(자동) 또는 `reviewed`(검수). 학습·평가는 검수본과 DMD 변환본만 사용. DMD 변환 라벨은 `auto`로 기록하고 검수 상태는 `rules`에 적음(5.4) |
| `driver_id`, `fps`, `frames` | 운전자 단위 분할 기준 / 실제 FPS(영상과 일치해야 함) / 전체 프레임 수. `driver_id`는 이미 만든 라벨의 값을 바꾸지 않음: NITYMED는 영상을 보고 붙인 `md01` 형식, DMD는 파일명의 운전자 번호(gC_14 → 14), 자체 촬영은 `self01`처럼 영문 접두사를 붙여 출처끼리 같은 문자열이 되지 않게 함 |
| `eye_closed` | 눈 감은 구간 목록(초 단위, 경계는 프레임에 맞춤), 없으면 `[]`. 눈 감김 정답 |
| `yawn` | 하품 구간 `{start, end, hand}` (0.5초 단위), `hand`는 손 가림 표시 |
| `head_down` | 고개 숙임 구간(프레임 단위). 눈이 안 보일 만큼 숙여도 여기에만 적고 `uncertain`에는 넣지 않음. DMD는 비움. NITYMED·자체 영상은 사람이 영상을 보고 표시한 '고개 숙임'과 '고개 숙임(눈 안 보임)' 구간. `eye_closed`에서는 '눈 안 보임' 구간을 뺌 |
| `uncertain` | 눈 상태를 알 수 없는 구간(가림, 어두움, 반사). 학습·평가에서 제외. DMD는 `undefined` 구간 |
| `conditions`, `segments`, `rules` | 안경·조명 등(DMD만 채움. NITYMED는 비어 있고 조명은 출처로 대신하며, 안경은 평가표에 쓸 때 필요한 만큼만 별도로 기록) / 보기용 단일 상태(학습에 쓰지 않음, DMD 변환 라벨에는 없음) / 변환 규칙과 수동 수정 기록 |

### 5.4 DMD 변환 (`dmd_convert.py`)

변환 규칙은 라벨 JSON의 `rules`에 함께 적습니다. DMD 라벨의 프레임 번호를 실제 FPS(29.76)로 나눠 초로 바꿉니다.

| 구분 | 처리 |
|---|---|
| 눈 감김 | `eyes_state/close`와 `closing` 프레임 구간을 `eye_closed`로 보고, 맞닿은 구간은 1개로 이음 |
| 눈 뜸 | `opening`은 뜸으로 봄(A 기준) |
| 쓰지 않음 | `blinks` |
| 하품 | `yawning` 구간. 프레임이 맞닿은 구간은 1회로 합치고, 일부라도 손이 있으면 `hand=true`. 시작·끝은 가까운 0.5초로 반올림 |
| 불확실 | `eyes_state/undefined` 구간. MediaPipe 얼굴 미검출은 넣지 않음(DMD가 눈 상태를 표시했으므로). 사람이 영상으로 눈이 보이는 것을 확인한 구간은 수동으로 제외하고 `rules`에 구간을 적음 |
| 고개 숙임 | DMD에 라벨이 없어 비움 |
| 조명 | DMD에 조명 항목이 없어 weather 값을 `conditions.lighting`에 대신 넣음 |
| 라벨 상태 | `auto`. 이전 라벨(v1)의 검수는 close 기준이라, closing을 더한 새 경계는 사람이 아직 보지 않았음 |

- A 기준은 반쯤 뜬 눈까지 감음으로 배우는 오경보를 줄이려는 선택입니다(gA_1 기준 최장 감김 A 2.22초 대 B 3.46초). 평가에서는 B 기준(`opening`도 감음)도 함께 보고합니다.
- 0.5초 미만의 짧은 감김(깜빡임)도 그대로 `eye_closed`에 남습니다. 깜빡임을 눈 감김으로 보는 것이 이 프로젝트의 기본 기준입니다(모델은 지금 상태만 답하고, 깜빡임이 경고로 이어지는지는 타이머의 단계 기준이 가립니다).

### 5.5 NITYMED 라벨링 절차

1. 검수 라벨로 `calibrate`를 돌려 임계값을 맞춥니다. 현재 `best_params.json`은 AI Hub 손 라벨 30클립으로 맞춘 값이고 DMD는 쓰지 않았습니다. 임계값을 고른 클립과 점수를 낸 클립이 같아 macro F1 0.911은 낙관적인 값입니다. `calibrate`가 저장소 밖 도구이고 val 규칙 성능이 기존 0.48배 기준보다 낮지 않아(README 실험 기록) 발표까지 이 값을 씁니다.
2. 마이크로슬립 2~3편에 `label`을 먼저 돌려 야간 오탐·미탐을 확인합니다.
3. 전체에 자동 라벨(`label`)을 만듭니다.
4. 검수: 눈 감김은 프레임 단위, 하품은 0.5초 단위로 고치고, 영상 전체를 0.5배속으로 훑어 놓친 눈 감김을 추가합니다. 깜빡임은 기본 기준에 따라 눈 감김으로 추가합니다. 단 11.04 기준 기존 NITYMED 라벨은 깜빡임을 정상으로 둔 상태이고 재라벨은 발표 이후로 미루므로, 이미 검수된 파일은 그대로 쓰고 새로 검수하는 파일부터 이 기준을 적용합니다. 고개 숙임은 `head_down`에 따로 적습니다.
5. 검수자, 사용 임계값, 수정 개수를 JSON에 기록하고, 10%는 두 사람이 따로 달아 일치도를 잽니다. 저장 후 필수 키와 `fps`를 점검합니다.

자동 라벨은 규칙의 결과라 순환 위험이 있습니다. 평가 정답은 DMD 라벨 중심으로 쓰고, NITYMED 평가용 운전자는 자동 라벨 없이 처음부터 답니다.

### 5.6 자동 라벨링 도구 흐름

| 순서 | 도구 | 하는 일 | 산출 |
|---|---|---|---|
| 1 | `dmd_convert` | DMD 라벨을 우리 형식으로 변환 | 눈 감김·하품 구간 |
| 2 | `extract` | 영상에서 프레임별 특징 11개 추출 | 특징 파일 |
| 3 | `calibrate` | 검수 라벨과 비교해 임계값 탐색 | `best_params.json` |
| 4 | `label` | 임계값으로 프레임별 상태 생성 | 자동 라벨(검수의 출발점) |
| 5 | 사람 검수 | 5.5의 4단계 | 검수 라벨 |
| 6 | `build_windows` | 특징과 라벨로 3초 창, 4클래스·하품 정답, 제외 마스크 생성 | `windows.npz` |

임계값과 변환 규칙은 공유된 `best_params.json`과 `dmd_convert.py` 하나만 씁니다. 이미 변환한 DMD 라벨 JSON이 기준이고, `dmd_convert.py`가 분할 행도 함께 만들고 `convert_labels.py`는 DMD 규칙을 적용하지 않습니다(재변환·재라벨 없음).

### 5.7 공유와 공개

영상, 특징, 라벨은 깃에 올리지 않고 비공개 팀 Google Drive로 공유합니다. DMD는 가공 데이터와 라벨을 공개하지 않고, 공개 데모 영상은 NITYMED(CC BY 4.0)와 자체 촬영으로 만듭니다. 자체 촬영은 실내 연기로만 하고 동의서를 받으며, 실제 졸음 상태로 운전하며 찍지 않습니다.

## 6. 데모, 로그, 운전 후 요약

### 6.1 streamlit-webrtc

| 항목 | 내용 |
|---|---|
| 역할 | 브라우저 웹캠 영상을 프레임 단위로 파이썬에서 받아 처리합니다(`video_frame_callback`). OpenCV·MediaPipe 처리를 콜백에 넣고 단계는 같은 화면에 표시합니다. |
| 주의 | 콜백은 별도 스레드입니다. 콜백 안에서 `st.*`를 쓸 수 없고, 공유 값은 `threading.Lock`과 공유 딕셔너리로 전달합니다. 클래스 방식(`VideoProcessorBase`)은 폐기 예정이라 콜백 방식을 씁니다. |
| 배포 | 원격 서비스는 HTTPS와 STUN(필요 시 TURN)이 필요해 로컬 시연으로 진행합니다. 막히면 OpenCV 창으로 대체합니다. |

### 6.2 판정 로그

실시간 판정을 기록으로 남깁니다. 로그 저장은 데모와 함께 만들고, 요약 화면은 핵심 평가가 끝난 뒤 만듭니다.

| 필드 | 내용 |
|---|---|
| `wall_time` | 실제 시각 |
| 영상 시각 | 타이머 기준 시각 |
| 단계 | 정상, 주의, 졸음 |
| 눈 감김 시간 | 연속 눈 감김(초) |
| 클래스 확률 | 모델 사용 시 4개 확률 |
| 이벤트 | 주의, 졸음, 하품 알림, 확인 필요, 판정 불가, 이어받기 |

### 6.3 운전 종료 후 요약

같은 로그를 시간순으로 모아 보여 줍니다. 새 점수를 만들지 않고 화면에 뜬 단계와 눈 감김 시간만 씁니다. 이벤트별 눈 감김 길이와 5분 구간별 이벤트 수를 막대로 보여 주는 안이며, 보고서의 예시 그림은 가상 데이터입니다.

## 7. 평가 방법

| 지표 | 목표 | 데이터·방법 |
|---|---|---|
| 졸음(3초) 이벤트 재현율 | 90% 이상 | 자체 연기 영상(3~7초)이 기본. NITYMED·DMD는 3초 이상 구간이 있는 만큼만 추가 |
| 주의(1.5초) 이벤트 재현율 | 값 보고 | 자체 연기 영상(1~2초) |
| 눈 감김 구간 F1 | 값 보고(규칙과 비교) | NITYMED 검수 + DMD 변환 라벨, 보정에 안 쓴 운전자. DMD는 A·B 기준 모두. 깜빡임 기준이 출처마다 달라(5.2) 출처별로 나눠 보고 |
| 하품 구간 검출·알림 | 손 가림 재현율 MAR 규칙 초과, 맨입 재현율 차이 0.05 이내, 오탐 시간당 10회 이하 | 하품 영상·정상 구간. 손 가림 따로 집계, 알림 횟수·오경보 |
| 고개 숙임 클래스 | 값 보고 | 조명별 혼동행렬(NITYMED 야간 대 DMD 주간), pitch 규칙과의 일치율. 맞지 않으면 모델 출력은 쓰지 않음 |
| 이어받기 규칙 | 값 보고 | 눈 감은 채 고개 떨어지는 장면의 경고 시점, 눈 뜬 채 고개 숙임의 오경보 수 |
| 오경보율 | 값 보고 | 정상 운전 구간(DMD, 자체 촬영)의 시간당 잘못된 경고 |
| 경고 지연 | 값 보고 | 기준 시간 도달 후 경고까지, 눈을 뜬 뒤 해제까지(Euro NCAP 허용 오차 0.2초 참고) |
| 처리 속도 | 15 FPS 이상 | 웹캠 실측, 규칙·모델 추론 시간 별도 |

- 평가 단위: 눈 감김 구간을 찾았는가를 기본으로 경계 오차도 냅니다. 눈 감김이 전체의 상당 부분이면서 정상과 치우쳐 있어(DMD gE_29는 31%, 파일마다 다르며 전체 비율은 변환 후 집계) 정확도 대신 F1과 이벤트 재현율을 씁니다.
- 모델이 규칙보다 나쁠 수 있습니다. 규칙을 흉내 낸 라벨은 규칙이 상한이므로 평가 정답은 DMD·검수 라벨로 하고, 지는 조건도 그대로 보고합니다. 실험 설정과 결과는 README 기록표에 남깁니다.
- 11.05에 눈 감김 F1을 목표에서 값 보고로 바꾸고 하품 목표를 정했습니다. val에서 눈 감김은 데이터마다 우열이 갈리고, 모델의 강점은 손 가린 하품에 있었기 때문입니다. Test2를 쓰기 전의 변경이며, 달성 여부는 Test2로만 판정합니다.

### 15 FPS 기준을 정한 이유

- 판정 단위가 0.5~3초라 15 FPS면 0.5초가 7~8프레임, 3초가 45프레임으로 충분합니다.
- 프레임 간격 약 67ms는 Euro NCAP 허용 오차 0.2초의 약 1/3입니다.
- 최소 눈 감김 0.1초(`min_close`)가 15 FPS에서 약 1.5프레임이라, 이보다 낮으면 짧은 눈 감김 판정이 거칠어집니다.
- 표준이 아니라 팀이 정한 실용 목표입니다. 데이터 FPS는 15로 리샘플해 맞추고, 하드웨어에 따라 보장되지 않으므로(선행 논문 Dlib+MLP 약 7 FPS) 웹캠에서 실측합니다.

- 브랜치: `main`에 직접 푸시하지 않고 PR로 병합합니다. 이름은 `feat/`, `fix/`, `docs/`로 시작합니다.
- 커밋: `YYMMDD 유형 : 내용` (예: `261030 FEAT : 자동 라벨 도구 추가`)
- 제외: 얼굴이 나오는 원본 영상과 데이터셋 파일은 올리지 않습니다.

**코드 반영 대기 (2026-11-05 기준).** 이 문서는 합의된 기준이고, 아래 항목은 코드가 아직 따라오지 않았습니다.

- 구현 완료, 병합 대기: `feat/head-pitch`(고개 숙임 상대 pitch 17.5도), `feat/dmd-convert`(`dataset/dmd_convert.py`), `feat/yawn-model`(하품 전용 모델의 학습과 실시간 연결, 하품 끊김 1.0초 병합과 길이 상한 7초), `feat/demo-final`(영상 데모·결과 그래프의 최종 구성, 마스크 스위치), `feat/baseline`(scikit-learn 기준선), `feat/rule-params`(`best_params.json` 연결), `feat/main-merge`(`main`과 이 문서의 합본). 모두 `feat/seq-pipeline` 위에 이 순서로 쌓여 있어, `feat/main-merge` 하나를 `main`에 병합하면 전부 들어갑니다.
- `calibrate`·`label`은 저장소 밖 이전 도구입니다.
- 판정 로그(6.2)의 `wall_time`·클래스 확률 기록과 선글라스 판정 불가(8장)는 코드에 없습니다. 선글라스는 기준값을 정할 영상이 없습니다.

**기준 정리 (2026-11-05).** 코드와 문서가 어긋났던 항목을 아래처럼 정했습니다.

- 파이프라인: 이 문서의 폴더 구조(`dataset/`, `auto_label/`, `demo/`, 최상위 `config.py`)와 `data/split.csv`를 따르는 `feat/seq-pipeline`이 기준입니다. `main`의 `train_lstm`·`share_lstm`과 창 단위 평가(`eval/window_eval.py`)는 `feat/main-merge`에서 이 구조에 맞춰 유지합니다.
- 분할 파일: 2.6의 `data/split.csv` 하나입니다. `split.json`은 `build_windows`가 내보내는 사본이고 입력이 아닙니다.
- DMD 분할: 2.6의 표대로 고정합니다. 16클립 전체를 평가 세트로 쓰지 않습니다.
- `best_params.json`: 5.5의 현재 값을 그대로 씁니다.
